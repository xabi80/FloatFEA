# CORPUS -- WHICH DECLARED FIELDS OF AN EXPORT CONFIGURATION `floatfea export` ACTUALLY READS
#
# What this file is a corpus of: shapes an export run configuration can take where a
# DECLARED value and the value the engine will actually compute at are different. One
# candidate per line. Test data only -- nothing here imports from `floatfea`.
#
# What a passing scan means: for every candidate below, `floatfea export` either produces
# a file at the declared value, or REFUSES by name before the engine starts. Neither
# "accepted and exported at something else" nor "accepted and silently dropped" is a pass.
# A refusal is a pass. A 26-minute solve followed by a refusal is a pass for this corpus
# and a separate finding about timing.
#
# Why this axis: `scripts/report_joint_reactions.py` hard-codes the sea state the solve
# runs at -- `WAVE_HEIGHT_MODEL_M = 0.484` (24.2 m full scale at lambda = 50) and
# `WAVE_HEADING_DEG = 0.0` -- and `floatfea export` builds the engine's argv out of the
# configuration. The argv carries `--dt`, `--out`, `--period` (one per DISTINCT declared
# period) and `--check`. It carries no heading and no height. So every field of a declared
# `load_cases.cases` entry except `T` is a candidate for this corpus by construction, and
# the two cross-checks the command does carry (`headings` against the BEM covered set, and
# `headings` against the cases' own heading) are checks between two CONFIG keys rather than
# between a config key and the engine.
#
# Measured by the reviewer at e4e233c, in a detached worktree, one candidate per cell, with
# `cli._covered_headings` returning `(0.0,)` and `floatsim_env.interpreter` substituted so
# no venv is needed, and `subprocess.run` spied: CAUGHT means the engine was never invoked.
# 13 candidates carry a measurement; 4 CAUGHT, 9 GREEN. The two rows that patch out the
# venv resolution are marked `reach=unmeasured` and are NOT in that ratio, because the
# substitution defeats the check they are about.
#
# ---------------------------------------------------------------------------------------

A1 | every case's H halved, 24.2 -> 12.0, nothing else changed | measured=GREEN | the engine is invoked with the same six --period flags and no height; the file is produced at 24.2 m
A2 | every case's H raised to 40.0, which is inside WAVE_HEIGHT's (0, 100] domain | measured=GREEN | the published envelope is then for a sea state 40% SMALLER than the one declared -- the unconservative direction
A3 | every case's H set to 0.0, the domain's lower edge | measured=GREEN | a zero-height wave is accepted and exported at 24.2 m
A4 | every case's H set to 99.0, just inside the ceiling | measured=GREEN | accepted; no steepness screen fires at export time because the export never reads H
A5 | two cases at one period with different H (T = 20 s at 24.2 and at 11.0) | measured=GREEN | `periods` is a set over `period_s`, so SEVEN declared cases become SIX --period flags and one declared case produces nothing, silently
A6 | the same case declared twice, byte-identical | measured=GREEN | deduplicated; benign today, and it is the same code path as A5
A7 | H declared in MODEL scale (0.484) by a reader who missed that WaveCase is full scale | reach=unmeasured | the schema admits it; 0.484 m is inside the domain
A8 | `H` omitted from one case while the others carry it | reach=unmeasured | `_require(item, "H", at)` should refuse; the question is whether the refusal names the case

B1 | heading 360.0 in BOTH `headings` and every case | measured=GREEN | `uncovered_headings` is modulo 360 so 360 is covered, and the two config keys agree exactly; the engine runs at 0.0 and the npz records 0.0, so this one is consistent
B2 | cases at 360.0 with `headings: [0.0]` | measured=CAUGHT | refused -- and the refusal compares the two lists with `!=`, while the covered-set reader next to it compares modulo 360. B3 | cases at -0.0 with `headings: [0.0]` | measured=GREEN | `-0.0 == 0.0` in Python, so the exact comparison passes; recorded because the same pair is REFUSED by `pipeline`'s signed-heading rule (FY1) on the run side
B4 | `headings: [0.0, 0.0]` | reach=unmeasured | `_parse_headings` refuses a repeat by name; the corpus row exists so the repeat axis is on the record
B5 | a BEM dataset covering [0.0, 45.0] (a future database), `headings: [45.0]`, cases at 45.0 | reach=unreachable-today | both config checks pass and the engine still runs at `WAVE_HEADING_DEG = 0.0`.
