# G1.0 — FloatSim output audit

**Gate:** G1.0 — a written finding, not code. **Blocks the schema lock.**
**Audited at:** HSP tag `floatfea-ref-1` (`25de7ce`)
**Date:** 2026-08-10

---

## Headline

`PLAN.md` §4 opened F1 with this audit on the expectation that it might shrink
the HSP work to a converter. **It did the opposite.**

**FloatSim writes nothing usable to disk today, and four of the schema's channel
groups describe quantities the simulator does not compute in any form.** Almost
everything needed exists in memory and is discarded at write time, so the work
is export rather than new physics — but it is export that has to be built, not
a converter over existing files.

## 1. What is written to disk today

| artifact | contents | usable? |
|---|---|---|
| `floatsim/io/results.py` | Milestone-0 **stub**; its own docstring says the per-channel schema "is intentionally not committed yet" | no |
| `Output(file=..., channels=[...])` in every deck | a deck field with **no consumer anywhere in the codebase** | no |
| `studies/platform-12buoy/fin_study/*.csv` | heave only: `t_s, center_heave_m, center_heave_acc_mps2, buoy_heave_m, buoy_heave_acc_mps2` | no |
| `fin_study/timeseries/*.npz` | point kinematics (`disp`, `vel`, `acc`) at 13 points | no |

**Zero load channels exist on disk.** Nothing in the required set can be
obtained by conversion.

## 2. What exists in memory

`IntegrationResult` (`newmark.py:109-137`) carries `t, xi, xi_dot, xi_ddot,
lam` and nothing else.

`lam` is the significant one: 16 joints × 4 constraint rows = **64
multipliers**, documented dt-free and physical. It is the joint-reaction
channel, exact and already computed, discarded at write time.

**Caveat that must travel with it:** `lam` is expressed against the constraint
Jacobian rows in each joint's own basis — *not* a force/moment 6-vector — and
the Jacobian is evaluated at the step **midpoint** `(x_n + x_{n+1})/2`
(`newmark.py:436`). The joint geometry and that midpoint convention must be
exported alongside, or the numbers cannot be interpreted.

## 4. Two findings from the final pre-lock channel walk

### 4.1 `μ(t)` is a required channel and does not exist

The radiation force actually applied is `A_inf·ξ̈ + μ(t)`. `A_inf` is in the
hydro database and `ξ̈` is exported, so the first term is recoverable. **`μ(t)`
is not.** It is a loop local — created at `newmark.py:391`, updated at `:449`,
consumed in the RHS at `:421`, and discarded. It appears in no return value.

This is not cosmetic. **G1.6 compares a reconstructed per-panel radiation
pressure field against the body-level radiation force FloatSim actually
applied.** Without `μ(t)` that comparison cannot be made, and G1.6 is
unenforceable for the radiation source — leaving the largest of the
BEM-sourced loads with no integrity check at all.

`μ(t)` is therefore a **required new export channel**, and it is the single
cheapest addition on this list: one array, already computed every step.

### 4.2 The platform has no mooring

`_deck_with_drag()` returns **`connections = 0`**, zero catenary lines. The
12-buoy platform is unmoored — 17 bodies joined by 16 `yaw_locked` joints, free
floating.

Consequences: `/mooring/` must be **optional**, not required; and the screening
metric "mooring line tension" (`load-interchange-v1.md` §5, `PLAN.md` §5) is
**inapplicable to this model** and must be struck from the metric list rather
than carried as a channel nobody can populate.

The same walk found "global base shear and overturning moment" to be inherited
from a fixed-jacket framing — **a floating platform has no base**. It is
replaced by the platform-interface resultant, which is what the metric was
reaching for and is derivable from the hub→platform joint reactions.

## 4.3 The hydro database is a FULL MULTI-BODY solve — checked

Asked because the consequence would have been invisible: if the database were a
single-body solve reused per buoy, hydrodynamic interaction between the twelve
buoys would be absent from every load FloatFEA ever sees, and **G1.6 would not
catch it** — FloatFEA would reconstruct the same single-body fields FloatSim
applied, and both would agree perfectly while omitting the same physics. That is
the KD-2 inheritance pattern: a limitation that passes every gate because both
sides share it.

**It is a genuine 12-body coupled solve.**

```
radiating_dof   72 entries   buoy1__Surge ... buoy12__Yaw
influenced_dof  72 entries   buoy1__Surge ... buoy12__Yaw
added_mass      (81 omega, 72, 72)
```

A 72×72 matrix could still be a block-diagonal assembly of twelve identical
single-body solves, so the coupling was **measured, not inferred**, at the
rotational mode (omega = 1.9302 rad/s, T = 3.255 s):

```
max |A| within own-body blocks     35.4204
max |A| in CROSS-BODY blocks        0.9454     = 2.7% of own-body
strongest pair                      buoy4 <-> buoy2
```

Cross-body terms are present at the **2.7%** level. Not block-diagonal, and not
negligible either — the same order as several effects this project has treated
as significant.

**Recorded as a positive finding.** "Checked, full multi-body database" is worth
writing down precisely because its absence would have been undetectable
downstream, and because the natural assumption from a 1488-panel *single-hull*
mesh is the opposite. The mesh is one hull; the solve is twelve.

## 5. Rotation state — a FloatSim defect, not a schema gap

FloatSim interprets `xi[3:6]` **three different ways**:

| module | interpretation |
|---|---|
| `morison.py:609-627` | ZYX-intrinsic Euler, via `quaternion_from_euler_zyx` |
| `joints.py:169-174` | rotation vector (axis-angle), via `Rotation.from_rotvec` |
| `hydrostatics.py:25` | linearised rotation vector, folded into `C` |

All three feed the same equations of motion and agree only to first order. At
the measured steady-state maximum, ‖θ‖ = 0.15657 rad, the two live
interpretations differ by **0.401%** on the 1.4574 m spar lever (0.29 m at full
scale).

Escalated to **LEVEL2-INTEGRATOR-UNWIRED** as primary evidence. It puts a floor
under G4.1 that cannot be exported away, because equilibrium *sums* sources
computed in disagreeing frames — while G1.6 stays clean, since it compares each
source against its own producer. That asymmetry is the signature distinguishing
an upstream defect from a mapping bug.

**Schema consequence (L1):** the rotation parameterisation is a **required
field per channel group**, not a documented convention. One simulator holding
three interpretations of one vector means a record carrying the loads but not
the interpretation carries half the information.

## 6. Inertia tensor reference point

`deck.py:88` declares the tensor **about the body reference point**;
`cluster_common.py:34` comments the values as "at single-buoy CoM";
`driver.py:222` passes `cog_offset_body=None`, i.e. *CoG at the reference
point*. The two points are **37.0 mm apart**.

Omitted: the parallel-axis term (0.164%, small) and the translation–rotation
coupling block `m·d = 1.061 kg·m` — a 4.05% coupling ratio, structural rather
than a magnitude error.

**G3.1a cannot catch a wrong reference point**, because both sides would be
internally consistent and consistently wrong. The record must therefore state
the tensor's reference point explicitly and the validator must reject its
absence.

Offered to KD-2's owner as a candidate mechanism *with* the magnitude that rules
it out at buoy scale — see `docs/findings/kd-2-candidate-mechanism.md`.

## 7. Determinism and the two-pass premise

No RNG exists anywhere in the solve path. Irregular seas are Phase 2
(`floatsim/waves/__init__.py`); only regular waves exist, so there is **no sea
state to screen** and no three-hour history to store.

The storage pressure that motivated two-pass deterministic replay
(`PLAN.md` §4) therefore **does not exist yet**. It arrives with Phase 2
irregular seas — which is also when the seed appears and determinism stops
being free. G1.4's replay half is reinterpreted accordingly; its numerical half
is promoted to G1.6.

## 8. What this means for the F1 build

Not a converter. Three additive HSP export modules — panel pressures, strip and
patch loads, solve state including `μ(t)` and the joint geometry — plus the
reader and validator in FloatFEA.

None of it touches the solve path, so G1.5 remains provable. The one unavoidable
contact is the strip/patch capture hook, which must be inert when disabled.

**This gate is closed.** The schema may now be locked.
