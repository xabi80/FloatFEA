**FL1 — STEP 1: CONFIGURATION AND ONE COMMAND (on existing data).**

(a) A declared config schema (YAML, validated, refusing out-of-range units with messages):

* `floatsim` — the deck reference (tag or path) and optional overrides, declared and
  recorded in provenance (ER1's mechanism generalised);
* `mass_distribution` — per body, either `f` with DY0's remainder rule and the PSD /
  realisability report, or an explicit list of line masses per member group plus lumped
  masses with positions. Body totals, CoG and inertia come FROM THE DECK, not the config;
  report the residual against the deck;
* `sections` — per member group (tube `D`, `t`), material (`E`, `G`, `ρ`, `Fy`);
* `load_cases` — the FloatSim runs (heading, `H`, `T` list, window rule), or a path to an
  existing dynamic-inputs npz;
* `code_check` — API RP 2A-WSD options (`K`, `C_m`, one-third increase);
* `outputs` — report, CSVs, and the optional analyses of FL2.

(b) The CLI: `floatfea run <config.yaml>` (build, static + dynamic, member forces, code
check, report) and `floatfea export <config.yaml>` (FloatSim runs → npz; needs the HSP
worktree, kept separate).

(c) `examples/platform12_placeholder.yaml` reproduces F6's governing `U = 1.71167`, F4's
envelope and the static analytic figures EXACTLY. This is a golden regression test in CI.

(d) Wall time of a full `run` on the example, reported.

**FL2 — STEP 2: GENERALITY.**

(a) Member topology from the config: a list of members (body, end A / end B by node, joint
label or coordinates, section group). The current star is generated by default. Statically
indeterminate frames are allowed. FG2's "forces independent of section" premise is then
CHECKED per run and reported, never assumed.

(b) Optional analyses: `required_section` (F6a's three searches, per group) and
`truss_sizing` (F6b's box/triangle sweep, per group), off by default.

(c) Headings: any list. `export` refuses a heading the BEM database does not cover, naming
what is missing. The governing envelope is taken over all headings and cases, and the
report shows the governing heading.

(d) The period band check (EZ2's associated-period rule and the breaking steepness) applied
per case and reported. Out-of-band cases are reported as sensitivity and never govern,
unless the config says otherwise.
