### 2e. Resizing cannot move the modelled mass today (DY0), which is why the loop is open

The builder back-computes an **equivalent density per body** so that `rho x A` equals the
deck's own line mass whatever the section is. Members are stiffness equivalents, not a
mass model. The consequence is exact and it is the reason GI exists: **a smaller section
carries the same mass at a higher equivalent density, so steel saved in sizing never
leaves the dynamics.** The R1 mass-reconciliation block is computed at the **declared**
`sections.groups` section rather than at the **sized** one, so three configurations with
different sized sections published identical equivalent densities. Step 2 is what makes
mass a function of the section; step 0 (a) measures how much that matters.

## 7. The FloatSim run environment (GJ1), and the resolution defect it closes

GJ1 ruled the FQ3 escalation: **restore the lock, do not re-base.** What that means
mechanically, and one thing it turned out to fix that the escalation had not seen.

### 7a. What the environment is

A venv at `.venv-floatsim`, built from the pinned worktree's own
`requirements-lock.txt` and nothing else. **Every FloatSim invocation by FloatFEA runs
under that interpreter**, and the run's provenance records its path and the lock's
`sha256`.

```

cmd    diff <(tr -d '\r' < lock-minus-editable.txt | sort -f) \
            <(tr -d '\r' < .venv-floatsim pip freeze | sort -f)
out    (empty) -- 39 of the lock's 40 lines, byte-identical
       numpy 2.4.4   scipy 1.17.1   xarray 2026.7.0   pandas 2.3.3
       capytaine 2.3.1   netCDF4 1.7.4   h5py 3.16.0   python 3.13.11

       exactly (a separate venv is fine)."

       reached. The lock's `sha256` is
       `c43531eedcb7a6f1ef601140da7c845908db6c28f7e7c15673796a07d9a311a7`.
```

**THE ONE LINE NOT INSTALLED, AND WHY IT IS NOT A SUBSTITUTION (SR).** The lock's
fortieth line is
`-e git+https://github.com/xabi80/HSP.git@928ae474...#egg=floatsim`. Installing it as
written would (i) clone HSP from the network into a **fourth** checkout, (ii) write an

exists to serve. It is left out, FloatSim comes from the pinned worktree on `sys.path`,
and this paragraph is the record. **No version is substituted: the same package is taken
at a strictly more pinned state.**

### 7b. The defect the empty venv closes, which FQ3 had not seen

```
claim  in the system interpreter, a bare `import floatsim` resolves to an undeclared
       tree 121 commits past the pin -- and in the new venv it resolves to nothing
cmd    python -c "import floatsim; print(floatsim.__file__)"
       python -c "import sys; sys.path.insert(0, HSP_RUNS); import floatsim; ..."
       .venv-floatsim/Scripts/python.exe -c "import floatsim"
out    system, bare           -> ...\HSP_code\floatsim\__init__.py
       system, worktree first -> ...\HSP-runs\floatsim\__init__.py
       locked venv, bare      -> ModuleNotFoundError: No module named 'floatsim'
rule   GI1: FloatSim runs "from the pinned HSP worktree (tag floatfea-ref-1)".
judge  The system interpreter carries an **editable install of `floatsim` pointing at
       `HSP_code`**, which `git describe` reads as `floatfea-ref-1-121-g71ed278-dirty`.
       Its `_EditableFinder` sits AFTER `PathFinder` in `sys.meta_path`, so the tree that
       answers depends on **whether the pinned worktree was put on `sys.path` first** --
       a property of call order, not of any declaration. The scripts that solve do insert
       it first and get the pin. A bare import does not.
```

**Why this is not a cosmetic difference between two checkouts.**

```
claim  how the two floatsim trees differ, in source files
cmd    diff -rq HSP-runs/floatsim HSP_code/floatsim | grep -v __pycache__
out    9 files with the same name and different bytes:
         bodies/joints.py  driver.py  hydro/morison.py  hydro/retardation.py
         io/deck.py  mooring/catenary_analytic.py  solver/equilibrium.py
         solver/newmark.py  waves/kinematics.py
       3 files and 1 directory present only in HSP_code (io/flr_*.py,
         validation/cases); 0 present only in HSP-runs
rule   GI1: FloatSim runs from the pinned worktree, so a difference in any file the
       npz path imports is a difference in the result.
judge  Nine differing files, not a version skew in a comment. **The first figure
       written here was "eleven", from reading the diff rather than counting it** --
       9 differ, 3 are additions, and `validation/cases` is a directory.
```

One of the nine is the radiation convolution:
`HSP_code` carries `fix: trapezoidal radiation convolution (was rectangular -> inflated
damping)` (`9fb5b33`, 2026-08-26), which the pin predates. The npz path imports
`RadiationConvolution` directly, so the two trees are **not numerically
interchangeable on the one path this milestone depends on**.

Two sites were measured resolving to `HSP_code` in a fresh process: the provenance field
`_hsp_tag()` (`export_f4_dynamic_inputs.py:173`), which then records the wrong tree in a
field EX0(a) requires, and `scripts/measure/g41_dynamic.py:256`, which would recompute a
residual with the **trapezoidal** convolution against a solve that used the
**rectangular** one. Neither has put a wrong number in a published artifact — the
committed provenance reads `floatfea-ref-1  (HSP-runs)` — because in every real run the
solve imports first. **That is a guarantee from call order, which is the shape FR1's
second head names: an input accepted and used other than as declared.**

**The locked venv removes the fallback rather than guarding it.** With no editable
install present, `floatsim` is importable only from a tree someone put on `sys.path`
deliberately, so there is no second tree for an order change to reach. Step 1 adds the
refusal that makes the remaining case loud: FloatFEA refuses if `floatsim.__file__`
resolves outside the declared worktree, and refuses if the running interpreter is not
the declared FloatSim environment — **a refusal rather than a re-exec**, per FZ's
standing ruling that an ambiguity is resolved toward refusing rather than silently
adjusting.
