## 0. The goal, and the one thing that makes it hard

GI0: FloatFEA runs FloatSim itself and sizes the platform and hub arms in a closed loop —

    sections → steel mass → body mass and inertia → FloatSim → export → FE + sizing → sections

until it converges.

**Why this is not a refactor.** Today the loop is open at both ends, and the open ends are
in opposite directions. Resizing cannot move the modelled mass at all (§2e), and the real
steel implied by a sized section disagrees with the mass the deck allocates to members by
**+10 % to +29 % on the platform and −31 % to −55 % per hub** — measured in the
pre-R2 acceptance work and re-measured as step 0 item (a). A loop that closes is a loop
whose fixed point is mass-consistent; nothing in R1 could even express that question.

### 2e. Resizing cannot move the modelled mass today (DY0), which is why the loop is open

The builder back-computes an **equivalent density per body** so that `rho x A` equals the
deck's own line mass whatever the section is. Members are stiffness equivalents, not a
mass model. The consequence is exact and it is the reason GI exists: **a smaller section
carries the same mass at a higher equivalent density, so steel saved in sizing never
leaves the dynamics.** The R1 mass-reconciliation block is computed at the **declared**
`sections.groups` section rather than at the **sized** one, so three configurations with
different sized sections published identical equivalent densities. Step 2 is what makes
mass a function of the section; step 0 (a) measures how much that matters.

## 3. Steps, and the gate each one has to pass

**Step 0 — measure only (GI3).** Gate: the one-screen report of GI3 (a)–(e), and the
`hsp_pin` fix of (e) — **the only code allowed in this step** — extended to all six sites
of §2c. Items: (a) the inertial vs joint-reaction share of each member's governing load,
from the npz's `m_xddot` and `accel`; (b) wall time of one FloatSim run and the projected
cost of one D4 iteration; (c) answered in §2a, re-stated with its command; (d) which
bodies carry buoyancy and where ballast could sit; (e) the path fix. **Then report and
stop (GI6).** No step-1 code until Xabier confirms or overrides D1–D4.

**Step 1 — export (FL2(c)).** Gate: `floatfea export` produces the dynamic-inputs file
from a FloatSim solve; exporting the reference run **reproduces the golden
dynamic-inputs file**, and `floatfea run` on that output gives **U = 1.71167** at
`platform:hub4_arm` ROOT. The heading refusal at `cli.py:1279` gets its input and fires.

**Step 2 — mass model and FloatSim invocation (D1, D2).** Gate, all four:
(i) FloatFEA writes the override file, builds the deck and runs FloatSim, read-only on HSP
source, every output in FloatFEA's own run folder;
(ii) **zero-change test** — feeding today's masses (ER0's, per §2a) reproduces the
reference run within FloatSim's own determinism, bit-identical on one platform per Q8;
(iii) **bookkeeping test** — member steel + non-structural + ballast = body mass,
*exactly*;
(iv) **draft check** — a deliberately un-ballasted case is **refused**, not warned.

**Step 3 — `floatfea optimize`.** Gate: the loop runs to D3 with an iteration table
(masses, ballast, governing member/U/heading, sections changed, FloatSim run ids, wall
time); output is the converged design **plus the full history**; a small case converges;
and an artificially oscillating case triggers the 0.5 under-relaxation and is reported as
relaxed. **A non-converged result is never reported as a design** — it is refused by
name.

**Step 4 — guide and witness.** Gate: a `docs/USER_GUIDE.md` section for the loop, and a
fresh-context agent that runs `floatfea optimize` from the guide alone. A failure fixes
the guide or the tool, never the witness.

## 4. Tolerances

Every value below goes in `floatfea/tolerances.py` with a named counter, per FZ rule 3.
**None of them exists yet**; they are declared here so the plan can be reviewed against
the list rather than against whatever the code grows.

| what | GI source | counter needed |
|---|---|---|
| static-equilibrium drift against the BEM reference draft and trim | D2 | yes — a BEM used off its draft is a silently wrong result, so the counter is an injected draft offset that must trip it |
| per-body mass change between iterations, `< 0.5 %` | D3 | yes |
| governing `U` movement between iterations, `< 0.01` | D3 | yes |
| iteration cap, `8`, and the 2-cycle oscillation detector | D3 | a cap is not a tolerance; the OSCILLATION TEST is, and it carries a counter |
| FloatSim determinism bound for the zero-change test | GI5 step 2 | bit-identical on one platform is an equality, not a tolerance — if it proves not to be, that is an escalation and not a widened number |

`D/t <= 300` and the candidate grid are **unchanged from R1** (D5) and are not re-derived
here.
