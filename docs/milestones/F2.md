# F2 — Beam solver core

**Status:** SKELETON, awaiting review
**Date:** 2026-08-14
**Gates owned:** G2.1 – G2.5
**Ladder:** rung 1 (V1.1–V1.3), rung 2 (V2.1–V2.6)
**Depends on:** nothing upstream — see §2

---

## 1. What gets built

Per `PLAN.md` §6 F2, and no more:

- **Nodes** and the model container.
- **3D two-node Timoshenko beam element** with shear deformation.
- **End releases** (pinned ends and partial releases).
- **Rigid links** via multi-point constraints.
- **Springs** and **point masses**.
- **Sparse assembly** and a **direct linear solve**.
- **Consistent mass matrix**, needed by G2.4 and untouched by any static test.

Element mathematics carries a comment naming its reference — textbook and
equation number — so the formulation can be checked against a source rather than
re-derived, per `CLAUDE.md` § Style.

## 2. Why nothing blocks this

F2 depends on nothing upstream, which is why `PLAN.md` §8 nominates it as the
parallel track when F1 slips. Two things that *could* have blocked it are already
settled:

- **Ladder rungs 1 and 2 are wired into CI** with `needs:` enforcing dependency
  order, so adding a verification case is a file drop.
- **The member local-axis convention is decided, enforced and tested**
  (`docs/conventions.md` § Member local axes; `floatfea/model/local_axes.py`).
  Local *x* from A to B, explicit orientation node required, `local y = z × x`,
  with the degeneracy guard firing on vertical members rather than silently
  switching reference axis. Every element sign convention depends on that triad,
  and retrofitting it would have meant re-deriving every sign.

The first tolerance entry, `MEMBER_ORIENTATION_DEGENERACY`, already exists with
its gate reference and a test that fails if it is raised to admit a vertical
member.

## 3. Gates

| gate | what it proves | ladder |
|---|---|---|
| **G2.1** | Six rigid-body modes at zero strain energy, tested as an eigenvalue *ratio* against the first flexible mode so it is mesh- and unit-independent | V1.1 |
| **G2.2** | Patch test — a constant strain state recovered exactly. Catches assembly, transformation and connectivity errors, which is why it sits below every accuracy comparison | V1.2 |
| **G2.3** | Cantilever tip deflection against closed form, **including the shear term on a deliberately stubby beam** where Euler-Bernoulli mislabelled as Timoshenko would pass V2.1 and fail here | V2.1, V2.2 |
| **G2.4** | Free-free natural frequencies against analytic values — the only gate that exercises the mass matrix | V2.5 |
| **G2.5** | Unit scaling: the same physical problem in a scaled unit system produces correctly scaled results. Catches hardcoded constants that no single-reference comparison will | V1.3 |

Plus **V2.3** (torsion, `TL/GJ` on a circular hollow section), **V2.4**
(three-dimensional coupling, where axial/bending/torsion couple through the
transformation — planar cases cannot see those sign errors), and **V2.6** (end
releases and rigid links, which are constraint-handling tests disguised as
element tests).

## 4. Ordering

The ladder is ordered by dependency, and F2 should be built the same way: **rung
1 before rung 2**. A patch-test failure makes every cantilever comparison
uninterpretable, so the assembly and transformation must be proven before any
accuracy number is believed.

## 5. Open questions for lock Q&A

**Q1 — Does geometric stiffness enter F2, or defer to Phase 2?**

`PLAN.md` §6 carries it as "designed for but may be deferred", and `WORKFLOW.md`
lists it under "still open, and cheap to defer". **It is less cheap now**, and it
belongs at the lock rather than in implementation, because *in or out changes the
element formulation* — the geometric stiffness matrix is assembled from the axial
force state, which means an element written without it and retrofitted later is
re-derived, not extended.

The configuration argues for taking it seriously: 50 m truss arms with slender
braces under axial load is where P-delta stops being a refinement.

> *Correction to the framing, not the question.* The **889 MN·m** figure
> associated with this argument is **withdrawn** — it was my arithmetic error,
> retracted in `docs/findings/mean-drift-and-screening.md` and in F1.md §8. It
> applied all three buoys' net force at 50 m when ~83% of that force is consumed
> supporting the rods and hub at the hub itself; the corrected static figure is
> **153 MN·m**, and the ×4 closure onto the truss placeholder confirms it.
> Further, a symmetric four-arm cross is self-equilibrated at the centre under
> symmetric load, so the governing case is the **antisymmetric differential**
> between clusters, of order **150–300 MN·m** — a *dynamic* quantity only the FE
> model can pin.
>
> **The argument for geometric stiffness survives the correction**: slenderness
> under axial load at 50 m span is what motivates it, not the moment magnitude.
> But the decision should not be taken against a retracted number.

**Q2 — Consistent or lumped mass?** G2.4 is the only gate that touches the mass
matrix, and the choice affects the frequencies it checks against. Consistent is
assumed above; confirm.

**Q3 — What is the local-axis triad for a *non-prismatic* or tapered member?**
The convention is fixed for prismatic members. The corrected §5 Q1 discussion
raises tapered truss chords as plausible, and the triad definition may need
extending before F3 rather than after.

**Q4 — Direct solve: which factorisation, and is the ordering deterministic?**
G2.1's eigenvalue ratio and the rung-6 golden files both key on reproducibility.
A permutation chosen by a heuristic that varies with library version would move
stored results without any code change — the same class of problem as the
Hypothesis seeding and BLAS thread count already pinned for G1.5.

## 6. Not in F2

Load mapping (F4), inertia relief (F4), the platform model itself (F3), and
anything requiring a `.flr` record. F2 is verified entirely against closed-form
and textbook cases with **no hydrodynamics anywhere in the loop**, which is the
property `PLAN.md` §1 identifies as the reason for keeping the two codebases
separate.
