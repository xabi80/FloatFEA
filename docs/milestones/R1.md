## 0. The goal, and what changes because of it

**Xabier, 13 Oct, via FL0: the tool must be ready for the final configuration, which will
be analysed later. No more analysis of the placeholder configuration.**

That is a change of subject, and it is worth stating precisely because it reverses the
burden of proof the last four increments operated under. F4, F6, F6a and F6b all answered
*what does this platform need?* — and every number they produced carries the placeholder
masses, one heading and an assumed grade. R1 answers *can this tool be pointed at a
different platform without editing Python?* The placeholder configuration stops being the
subject and becomes **the regression fixture**: FL1(c) requires the example config to
reproduce F6's and F4's figures exactly, which is how the generalisation is held to
changing nothing.

**So R1 adds no engineering finding.** If it produces one, that is a defect in the
generalisation, not a result.

## 1. The directive, verbatim

**FL1 — STEP 1: CONFIGURATION AND ONE COMMAND (on existing data)**

**(a)** A declared config schema (YAML, validated, refusing out-of-range units with
messages):

* `floatsim`: the deck reference (tag or path) and optional overrides, declared and
  recorded in provenance (ER1's mechanism, generalised);
* `mass_distribution`: per body, either `f` (with DY0's remainder rule and the PSD /
  realisability report) or an explicit list of line masses per member group plus lumped
  masses with positions. **Body totals, CoG and inertia come FROM THE DECK, not the
  config.** Report the residual against the deck;
* `sections`: per member group (tube `D`, `t`), material (`E`, `G`, `ρ`, `Fy`);
* `load_cases`: the FloatSim runs (heading, `H`, `T` list, window rule), or a path to an
  existing dynamic-inputs npz;
* `code_check`: API RP 2A-WSD options (`K`, `C_m`, one-third increase);
* `outputs`: report, CSVs, and the optional analyses (FL2).

**(b)** The CLI: `floatfea run <config.yaml>` (build, static + dynamic, member forces, code
check, report) and `floatfea export <config.yaml>` (FloatSim runs → npz; needs the HSP
worktree, kept separate).

**(c)** `examples/platform12_placeholder.yaml` reproduces F6's governing `U = 1.71167`,
F4's envelope and the static analytic figures EXACTLY. **This is a golden regression test
in CI.**

**(d)** Wall time of a full `run` on the example, reported.

**FL2 — STEP 2: GENERALITY**

**(a)** Member topology from the config: a list of members (body, end A / end B by node,
joint label or coordinates, section group). The current star is generated by default.
**Statically indeterminate frames are allowed.** FG2's "forces independent of section"
premise is then **CHECKED per run and reported, never assumed.**

**(b)** Optional analyses: `required_section` (F6a's three searches, per group) and
`truss_sizing` (F6b's box / triangle sweep, per group), **off by default.**

**(c)** Headings: any list. `export` refuses a heading the BEM database does not cover,
naming what is missing. The governing envelope is taken over all headings and cases, and
the report shows the governing heading.

**(d)** The period band check (EZ2's associated-period rule and the breaking steepness)
applied per case and reported. Out-of-band cases are reported as sensitivity and never
govern, unless the config says otherwise.

**FL3 — STEP 3: USER GUIDE AND WITNESS**

**(a)** `docs/USER_GUIDE.md`: install, quickstart, every config field with its unit and
range, the run and export commands, the outputs, how to read the report, and the
limitations (stand-in sections, linear Airy waves, rigid-body FloatSim, superstructure
only, the API WSD screen, no joint checks).

**(b)** **WITNESS (DO3):** a fresh-context agent with no history clones the repo, follows
ONLY the guide, runs the example, and must reproduce FL1(c)'s figures. Its transcript goes
in `docs/closure/R1.md`. **If it fails, the guide or the tool is fixed, not the witness.**

### 2c. FG2's premise, CORRECTED: it is true of `max U`, and FALSE of the member forces

**This is the plan's one substantive observation, it decides what FL2(a)'s per-run check
must measure, and an earlier revision of this plan had it wrong** — it said the premise
holds by symmetry plus uniform sizing and stopped there. The symmetry part is right. The
stopping is not, because F6a already measured the premise FAILING on the dynamic case:

```
claim  what F6a measured the premise to be, as its closure artifact records it
cmd    docs/closure/F6a.md:199-215
out    static  : holds to round-off -- `1.742356e-15` relative at the worst of the three
                 searches, over a `2.62x` span of platform area (the deliverable publishes
                 `1.608328e-15`, which is answer (iii)'s and not the worst)
       dynamic : "On the dynamic case the member forces MOVE."
       what does not move is `max U`, after re-selecting which instant governs at the
       sized section: largest change across all six answers `3.496e-06`, smallest margin
       `1 - max U` across all six `4.220e-03`, so the motion is `1207x` inside the
       tightest margin
rule   FG2 as asserted: "section choice does not change the loads or the member forces"
judge  **as asserted the premise is FALSE, and F6a says so.** The mechanism is recorded
       and it is specific: the d'Alembert field is an ACCELERATION, and what turns it into
       a load is `element_equivalent_load = M_e @ a_e` with the consistent element mass
       matrix, whose rotary terms are `rho_eq * I = mu * r^2`. **`r` moves with the
       section even though `mu` is held** by `_build_body`'s back-computed density. So
       the forces move today, in the determinate symmetric star, with no indeterminacy
       anywhere near it.
```

**What survives is a narrower premise about a different quantity:** `max U` is insensitive
to the section, the member forces are not. So a check written as "did the member forces
change" would fire on the existing example, be correct to fire, and be useless.

**And indeterminacy adds a SECOND failure mode, which symmetry currently hides.** The
static half holds to `1.742356e-15` because the four arms are geometrically identical and
sized uniformly per body, so the one redundancy splits equally whatever the section is. Lift
either condition — a non-uniform section group, or a topology whose redundancy is not
symmetric — and relative stiffness redistributes the forces by an amount that is not
round-off and not bounded by anything F6a measured.

### 2c-i. The premise is not CHECKED, it is RETIRED (DIRECTIVE FM0)

**An earlier revision of this plan put a threshold on the premise and sent its derivation
to step 2's lock Q&A. FM0 rules otherwise, and the ruling is better than the plan was.**

> FG2's premise is NOT checked by a threshold. The sizing analyses (`required_section`,
> `truss_sizing`) use fixed forces only to **PROPOSE** candidates. The tool then
> **RE-SOLVES** the FE model (static + dynamic) with the selected sections and reports
> `max U` from that re-solve. If `U > 1.0`, it steps the section up and re-solves, looping
> until `U ≤ 1.0` or the grid is exhausted (and then refuses). Report the iteration count
> and the fixed-force vs re-solved `max U`.

**Why this is right where a threshold was not.** A threshold asks *is the premise true
enough to trust the fixed forces?* — a question whose answer depends on the frame, the
section spread and the heading, and which no single number answers for an unknown final
configuration. The re-solve does not ask it at all. The fixed-force pass becomes a
**proposal mechanism** whose only duty is to land near the answer, and correctness comes
from the re-solve, which is an ordinary FE solve at the sections actually chosen.

So the two failure modes above both stop mattering: the dynamic rotary-inertia motion
(`r` moving with the section) and the indeterminate redistribution are both simply *present
in the re-solve*, whatever their size. **Determinate and indeterminate frames take the same
code path**, which is the property a tool for an unknown configuration needs.

**And it needs no new tolerance.** `U ≤ 1.0` is API RP 2A-WSD's own acceptance, not a
comparison epsilon; the grid is the declared section list; the loop terminates on the grid
or refuses. Nothing is chosen to make two numbers agree.

**What is reported** (and this is the honest-output requirement, not a nicety): the
iteration count, and **both** `max U` values — the fixed-force one the proposal was made
on and the re-solved one the answer rests on. A large gap between them is a finding about
the configuration, and it is exactly the finding a threshold would have hidden by either
passing or refusing.

**Exhaustion refuses.** If the grid runs out with `U > 1.0`, the tool says so and names the
group and the governing case. It does not report the last candidate as if it were a
section, and it does not extend the grid on its own.

**Step 2 — generality.** Gate: member topology from the config with the star as the

refusing by name, and reporting the iteration count with both the fixed-force and the
re-solved `max U` (§2c-i, FM0); the optional analyses off by default; headings as a list
with `export` refusing uncovered ones by name; the band check per case with out-of-band
cases unable to govern. **Line 72's "CHECKED per run and reported" is satisfied by the
re-solve itself** — the premise is not relied on, so there is nothing left to check.

**Step 3 — guide and witness.** Gate: a fresh-context agent with no history clones the
repo, follows **only** `docs/USER_GUIDE.md`, and reproduces step 1's five fixtures. Its
transcript goes in `docs/closure/R1.md`. **A failure fixes the guide or the tool, never
the witness.**

## 4. Tolerances

**None expected, under FM0.** An earlier revision of this plan declared one for step 2 —
a threshold on the premise check — and FM0 retired the check that needed it (§2c-i). The
re-solve loop introduces no comparison: `U ≤ 1.0` is API RP 2A-WSD's own acceptance
criterion, the candidate grid is the config's declared section list, and the loop
terminates on the grid or refuses.

Everything else that looks like a number here is not a tolerance either. FL1(c)'s
"exactly" is a golden comparison; the config's ranges are declared validation bounds;
`K`, `C_m` and the one-third increase are the clause's own options.

**If anything in execution needs a value chosen to make two numbers agree, that is a
tolerance and it stops and asks.** It does not get added quietly to make the re-solve loop
converge — a loop that will not converge is a finding about the configuration.

## 5. What this milestone does NOT do

It analyses nothing. No new engineering finding is expected or wanted — if the
generalisation produces a different number for the placeholder configuration, that is a
defect in R1 and not a result about the platform. The final configuration is analysed
later, under its own directive.
